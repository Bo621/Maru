# 마루(Maru) SNS 재설계 — 설계 문서

작성 2026-07-30 · 마감 2026-07-31 · 브랜치 `feat/maru-feed`
개정 2026-07-30 (코덱스 리뷰 1회차 반영)

## 문제

마루는 GIWA Sepolia의 POI 결정 기록을 읽어 보여주는 읽기 전용 소비자 화면이다.
Track 02(CONSUMER/SOCIAL) 지원작인데 **소셜로 읽히지 않는다.** 원인은 셋이고, 셋 다 UI만의 문제가 아니다.

### 원인 1 — 화면이 기록 우선이다

피드 행이 상태 도장(`state-seal`)으로 시작하고, 발행자는 잘린 16진수 링크다.
사람이 아니라 레코드가 주인공이라 원장(元帳)으로 읽힌다.

### 원인 2 — 데이터가 데모로 쓸 물건이 아니다

2026-07-30 기준 체인 실측 (`.env.example`의 스키마·배포 블록 기준, 전량 조회):

```
결정 총계          5건
발행자 수          1명 (0xA1Cb5CbC…)
parents 있는 결정   1건 (0x5d2a066cec… → 부모 0xe015bb0a…)
도장 검증된 결정    5건 (전부)
reasonCommitment   5건 전부 ZERO
지표                5건 전부 BTC_PRICE_KRW_AT_END (KRW, decimals 0)
연산자              4건 `>` (op=0), 1건 `≥` (op=1)
임계값              5건 전부 1
```

세 가지가 동시에 걸린다.

1. **발행자가 한 명**이면 어떤 디자인을 씌워도 피드가 아니다.
2. **5건 전부 도장 검증**이라 `verified=1` 필터가 아무것도 거르지 않는다.
   심사자 눈에는 필터가 고장 난 것으로 보인다.
3. **임계값이 전부 1원**이다. "비트코인 원화가격이 1원을 넘는다(4건) / 1원 이상이다(1건)" —
   자명하게 참인 시험 데이터다. 발행자 수를 늘려도 이 조건이 그대로면 화면이 설득하지 못한다.

그리고 `reasonCommitment`가 전부 ZERO이므로 **기존 5건에는 공개할 이유가 애초에 없다.**
salt 분실 문제가 아니라 커밋 자체가 없다. REASON 원문 기능은 전적으로 신규 발행분에만 걸린다.

확인된 좋은 소식: `time=1785342462 < windowStart=1785342755`.
커밋이 관측 구간 시작 293초 전에 고정된 것이 데이터로 확인된다.
"결과를 알기 전에 고정됐다"는 주장은 뒷받침된다.

### 원인 3 — 미학이 "아카이브"다

현재 토큰은 한국 공문서/장부 미학이다: 크림 종이(`--paper`), 먹색(`--ink`),
인주 빨강(`--seal`), 궁서 계열 세리프(`Gowun Batang`), 7rem 세로 괘선.
의도적이고 독특하지만 **본문까지 세리프**라 "옛날 문서"로 읽힌다.

## 2. `DecisionCard` — 인물 우선 카드

피드와 패스포트가 공유하는 단일 컴포넌트. `src/card.tsx`.

### 2.1 구조

```
┌ 01 ────────────────────────────────────────────┐
│ (아바타) 0xA1Cb…5CbC  ● 도장 검증 TESTNET FAUCET │
│                                       3시간 전  │
│                                                 │
│  "8월 FOMC 전까지는 위로 본다. 현물 유입이…"    │  REASON 원문
│   이 문장의 해시가 결정에 기록된 커밋과 일치     │  (검증 통과 시에만)
│                                                 │
│  비트코인 원화가격(종가)이 89,291,000원을 넘는다 │  숫자 그대로
│  관측 07-29 16:32 → 16:42 UTC                   │  UTC 유지
│                                                 │
│  [기한초과]  [이전 판단 2]  [결정 열기 ↗]       │
└─────────────────────────────────────────────────┘
```

### 2.2 지금과 달라지는 것

1. 아바타 + 발행자 주소가 **맨 앞**. 상태 도장은 하단 배지로 내린다.
2. 시각은 상대시간("3시간 전"). `<time dateTime>`과 `title`에 UTC ISO를 넣는다.
   **관측 구간은 UTC 문자열 그대로 유지.**
3. REASON 원문이 있고 §3.1 검증을 통과하면 인용 블록으로 최상단 본문에 놓는다.
4. 조건식을 한국어로 읽히게 하되 **수치는 한 자리도 바꾸지 않는다**(§3.3).
5. 스레드가 있으면 배지로 표시. 문구는 "이전 판단" — "답글"이 아니다(§3.4).

카드는 기존 `data-feed-row` / `data-kind` / `data-settled-count` / `data-verification`을
전부 유지하고 두 개를 **추가**한다(§8.4가 읽는다).

| 속성 | 값 | 비고 |
|---|---|---|
| `data-attester` | 소문자 발행자 주소 | 고유 발행자 수 계산의 안정된 추출점 |
| `data-block-number` | 십진 문자열, `blockNumber`가 `null`이면 **속성을 안 붙인다** | 정렬 검사 |

`AttestedLog.blockNumber`는 `bigint | null`이다(`src/read.ts:24`).
`feedData.ts`의 정렬은 이미 `?? -1n`로 null을 맨 뒤로 보낸다.
E2E 정렬 검사는 **속성이 있는 행만** 대상으로 하고, 없는 행은 건너뛴다.
없는 속성을 `0`으로 읽으면 정렬이 깨진 것처럼 보인다.

`data-attester`가 없으면 발행자 수를 세는 유일한 추출점이
주소 링크의 `aria-label="발행자 0x…"` 하나뿐이다(`src/feed.tsx:76`).
카드를 다시 쓰면서 그게 사라지면 §8.4가 조용히 못 쓰게 된다.

### 2.3 REASON 배지가 주장하는 것과 주장하지 않는 것

`verifyReveal`은 **해시 일치만** 증명한다. 화면 문구가 그 이상을 암시하면 안 된다.

| `verifyReveal`이 증명하는 것 | 증명하지 않는 것 |
|---|---|
| 이 문장의 해시가 결정에 기록된 커밋과 같다 | 문장이 참이다 |
| 발행자 주소가 프리이미지에 들어가 타인의 커밋 복사본은 실패한다(CT18) | 발행자가 정직하다 |
| | 커밋이 **언제** 고정됐는지 |
| | 이 이유가 이 결정에만 쓰였다 |
| | 공개하지 않은 다른 판단이 없다 |

**시점은 `verifyReveal`이 증명하지 않는다.** "결과를 알기 전에 고정됐다"는
별개의 온체인 사실 — `attestation.time < windowStart` — 에서 나온다.
두 주장을 한 배지에 섞지 않는다. 시점 배지는 §3.1의 별도 가드를 통과할 때만 붙인다.

특히 **재사용(replay)은 막히지 않는다.** 커밋 프리이미지는 결정 UID·부모·구간·지표를
묶지 않으므로, 같은 발행자가 같은 이유를 여러 결정에 커밋할 수 있고 같은 공개 파일이
그 전부에서 통과한다. 배지 문구는 "이 결정의 고유한 이유"라고 말하지 않는다.

또한 **salt의 무작위성은 검증할 수 없다.** 약한 salt는 공개 전 사전 추측을 허용한다.
테스트넷 데모 범위에서는 수용하되, 이 한계를 문서에 남긴다.

### 2.4 번호 마커

`number-details` 규칙: 두 자리(`01`), mono·저대비, 카드 좌상단 고정.
헤딩보다 약하게 — "decorative numbers must not compete with headings."

## 3. 신규 모듈

전부 `src/`에 놓고 각각 `test/`에 테스트를 둔다.

| 파일 | 책임 | 순수성 | 의존 |
|---|---|---|---|
| `src/sentence.ts` | 결정 필드 → 한국어 문장 | 순수 | `@poi/core`(METRICS) |
| `src/revealVerify.ts` | (salt, payload) → 커밋 대조 | 순수 | `@poi/core` |
| `src/revealLoad.ts` | 공개 파일 가져오기 | 부수효과 — `fetch` 주입 | `revealVerify` |
| `src/thread.ts` | `parents` → 스레드 조립·깊이 | 순수 | 없음 |
| `src/relativeTime.ts` | 상대시간 문자열 | 순수 | 없음 |
| `src/avatar.tsx` | 주소 → 결정론적 아이덴티콘 | 순수 | `blo` |

### 3.1 `revealVerify.ts` — 이 스펙에서 가장 중요한 규칙

**공개 파일에서 받는 값은 `salt`와 `payload` 둘뿐이다.**

`tag`·`chainId`·`attester`는 파일에서 읽지 않고 앱이 신뢰할 수 있는 출처로 직접 만든다.

```
verifyReasonReveal(file, decision) → payload | undefined

  입력 조립 (파일 아님):
    tag      = "REASON"              상수
    chainId  = CHAIN.id              config.ts
    attester = decision.attester     온체인 attestation
    salt     = file.salt             ← 파일
    payload  = file.payload          ← 파일

  거부 조건:
    decision.reasonCommitment === ZERO_UID  → undefined
    verifyReveal(...) === false             → undefined
    verifyReveal(...) 예외                  → undefined
```

**시점 배지는 별개의 가드를 통과할 때만 붙인다.**

```
preCommitted(decision) = decision.time < decision.windowStart
```

이 값이 거짓이면 "결과를 알기 전에 고정" 문구를 렌더하지 않는다.
해시 일치와 시점은 서로 다른 근거에서 나오므로 배지도 분리한다(§2.3).
현재 온체인 5건은 전부 이 가드를 통과한다(`time` 대비 `windowStart`가 290~293초 뒤).

**`verifyReveal`은 두 가지로 실패한다.** 형식이 멀쩡한데 해시가 다르면 `false`를 반환하고,
입력 형식이 깨졌으면 **예외를 던진다.** 두 경로를 다 막아야 한다. 던지는 지점:

```
core/src/commitment.ts:40  requireHexBytes  salt가 16바이트 hex가 아니면 CommitmentError
core/src/commitment.ts:60  chainId <= 0
core/src/commitment.ts:62  attester가 주소 형식이 아님
```

`tag`를 파일에서 받으면 임의의 32바이트 hex가 들어올 수 있다(`CommitmentInput.tag`가
`CommitTagName | Hex`이다). 그래서 상수로 고정한다.
호출은 반드시 `try/catch`로 감싼다 — 조작된 JSON 하나가 카드 전체를 죽이면 안 된다.

검증을 건너뛰면 이 기능은 자기소개란이 되고 제품의 명제가 무너진다.

### 3.2 `revealLoad.ts` — 부수효과 격리

공개 파일은 `public/reveals/<decisionUID>.REASON.json`에 정적으로 둔다.

```
loadReasonReveal({uid, fetchImpl}) → RevealFile | undefined
```

`fetchImpl`을 주입해 테스트에서 네트워크를 쓰지 않는다.
**`signal`을 받지 않는다.** 받으면 한 호출자의 취소가 공유 요청을 통해
다른 호출자에게 전파된다. 취소 수단을 API에서 아예 없앤다.

| 상황 | 동작 |
|---|---|
| 404 | undefined (정상 경로) |
| 그 외 비 2xx | undefined + `console.warn` |
| 네트워크 실패 | undefined |
| JSON 파싱 예외 | undefined |
| 응답 64KB 초과 | 읽지 않고 undefined |
| `version !== "poi.reveal.v1"` | undefined |
| 같은 UID 동시 요청 | 요청 맵으로 중복 제거 (`feedData.ts`의 라벨 캐시와 같은 방식) |
| 컴포넌트 언마운트 | **공유 요청을 취소하지 않는다.** 호출자 쪽에서 결과를 버린다 |

마지막 행이 중요하다. 요청 중복 제거와 `AbortController` 취소를 같이 쓰면
**한 호출자의 언마운트가 다른 모든 호출자의 요청을 죽인다.**
공유 요청은 끝까지 두고, 언마운트한 호출자만 `current` 플래그로 결과를 무시한다
(`useFeedRows.ts:23`가 이미 쓰는 방식). 취소가 꼭 필요해지면 참조 카운트를 쓴다.

### 3.3 `sentence.ts` — 숫자는 건드리지 않는다

`BTC_PRICE_KRW_AT_END > 89,291,000`을
`비트코인 원화가격(종가)이 89,291,000원을 넘는다`로 바꾼다.

**반올림·축약·단위 환산을 하지 않는다.** `8,929만 원`으로 줄이면 1,000원이 사라진다.
커밋된 조건을 바꾸는 표기는 이 제품에서 가장 하면 안 되는 일이다.

- 수치는 `presentation.ts`의 `formatScaled`가 만든 문자열을 **그대로** 쓴다
- 지표명과 연산자만 한국어로 바꾼다
- METRICS에 없는 `metricId`는 기존 `formatCondition` 출력으로 폴백한다

**선행 작업**: `formatScaled`는 현재 `src/presentation.ts:13`의 비공개 함수다.
`export`로 열거나 공용 모듈로 옮겨야 `sentence.ts`가 재사용할 수 있다.
숫자 포맷을 두 벌 만들면 두 화면이 서로 다른 수치를 보여줄 수 있으므로 복제하지 않는다.

### 3.4 `thread.ts`

`POIDecisionResolver.sol:143` — "같은 지갑의, 더 이른, 살아 있는 결정만 부모가 될 수 있다."

## 6. 데이터 시딩 — 임계 경로, 가장 먼저 한다

faucet·트랜잭션·부모 제약·finality가 가장 통제하기 어렵다.
장식 작업에 시간을 쓰기 전에 실패를 먼저 발견한다.

`~/GIWA/web`의 지갑 연결 발행 화면을 쓴다. 컨트랙트는 건드리지 않는다.

1. 새 지갑 2개에 GIWA Sepolia faucet ETH 확보
2. **미검증** 상태로 결정 3~4건 발행
   (`POIDecisionResolver.sol:166` — "B4 커밋 시점의 검증 상태 스냅샷. **필수가 아니다**")
3. **현실적인 임계값**으로 발행한다. 현재 온체인 데이터는 전부 `> 1 KRW`라 데모로 못 쓴다
4. 발행 시 **REASON 커밋을 반드시 설정**하고 salt를 보관한다
   (기존 5건은 `reasonCommitment`가 ZERO라 원문을 붙일 방법이 없다)
5. 기존 지갑으로 `parents`를 단 결정 1~2건 추가 발행 → 스레드 2~3단
6. REASON 공개 파일을 뽑아 `public/reveals/`에 넣는다

### 6.1 정직성 — 지갑은 사람이 아니다

한 사람이 쥔 주소 두 개는 사용자 두 명이 아니다.
화면과 지원서에 **"데모 페르소나"**라고 명시한다.
"발행자 2~3명"이라고 쓰면 이 프로젝트가 내내 지켜온 원칙을 스스로 깬다.

### 6.2 E2E와의 결합

S2→S3는 필터가 누적된 채 이어진다(§8.3). 따라서 체인에
**`verified=1`이면서 활성 정산이 1건 이상인 발행자의 기한초과 결정**이 반드시 있어야 한다.
현재 `0xA1Cb5CbC…`가 이 조건을 만족한다. 시딩이 이걸 깨면 안 된다.

### 8.4 기존 E2E가 자기 시나리오를 증명하지 않는다 — 보강한다

`e2e/feed.spec.ts`의 단계 이름과 실제 단언이 어긋나 있다.

| 단계 이름이 주장하는 것 | 실제로 검사하는 것 | 빠진 것 |
|---|---|---|
| S1 "여러 지갑의 결정을 **시간 역순**으로" | 행이 0개가 아님 | 지갑이 2개 이상인지, 정렬이 내림차순인지 |
| S2 "필터를 켜면 검증된 것만 **남는다**" | 남은 행에 라벨이 있음 | 필터가 **무언가를 걸렀는지** |
| S3 "결과를 안 올린 발행자가 **사라진다**" | 남은 행이 조건을 만족함 | 발행자가 실제로 **줄었는지** |

지금 상태로는 시딩한 새 데이터가 제품 서사를 깨도 테스트가 초록색으로 남는다.
PLAN.md가 직접 쓴 원칙 — "필터를 지웠을 때 테스트가 깨지지 않으면 그 테스트는 무의미하다" —
을 E2E에도 적용한다.

**보강 (§8.3의 기존 단언은 전부 유지한 채 추가):**

**모든 보강 단언은 `[data-feed-row][data-kind="decision"]`만 센다.**
오류 행(`data-kind="error"`)을 섞으면 안 된다 — 오류 행 하나가 사라진 것만으로
"행 수가 줄었다"가 통과해서, 결정이 하나도 안 걸러졌는데 S2가 초록색이 된다.
기존 §8.3의 S2·S3도 이미 결정 행만 센다. 기준선도 같은 셀렉터를 쓴다.
`data-attester`는 오류 행에도 붙지만, 발행자 집합 역시 결정 행에서만 모은다.

먼저 **필터 없는 상태에서 기준선을 기록한다** — 결정 행 수, 고유 발행자 집합.
보강 단언은 전부 이 기준선 대비로 잰다.

- S1: 고유 발행자 주소 수 ≥ 2 (결정 행의 `data-attester`)
- S1: 결정 행의 순서가 `data-block-number` 내림차순
- S2: `verified=1` 적용 후 결정 행 수 < 기준선 결정 행 수
- S3: `match≥1`을 **기준선에서** 적용했을 때 고유 발행자 수 < 기준선 발행자 수

**S3를 S2 결과 위에서 재면 안 된다.** S2가 미검증 지갑을 전부 걷어내면
검증된 발행자 하나만 남고, 그 발행자는 활성 정산을 갖고 있어 `match≥1`이
아무도 못 줄인다. S3의 주장("결과를 안 올린 발행자가 사라진다")은
필터 없는 피드 대비로만 검사할 수 있다.

따라서 S3 보강은 **별도 테스트로 분리**한다 — S2의 상태를 물려받지 않는다.
§8.3의 기존 S3(S2에서 이어지는 누적 필터 경로)는 그대로 둔다.

**시딩 조건**: 새로 발행한 미검증 결정은 **활성 정산을 등록하지 않은 상태로 둔다.**
그래야 기준선에 `settledDecisionCount === 0`인 발행자가 존재하고 S3가 검사할 대상이 생긴다.

S1·S2·S3 보강은 §6 시딩이 성공한 뒤에만 통과한다. 이건 결함이 아니라 의도다 —
시딩이 실패하면 테스트가 그 사실을 알려야 한다.

### 8.5 신규 E2E

기존 S5(PLAN.md)를 **밀어내지 않고 유지**한다.

- S5 (기존 유지): 피드 → 패스포트 → 결정 상세 → 검증하기
- S6 (신규): 스레드 배지 → 상세 → 부모 판단 — 구현 7단계에 속한다

S6와 S7은 서로 다른 구현 단계에 딸린다. 한 단계에 묶지 않는다.

## 9. 구현 순서

각 단계 끝에서 `pnpm test`와 `pnpm build`를 돌린다.
**임계 경로를 먼저 소진하고, 장식을 마지막에 둔다.**
중간에 시간이 떨어져도 앞 단계까지로 배포 가능하다.

| | 무엇 | 왜 이 순서인가 |
|---|---|---|
| | 무엇 | 의존 |
|---|---|---|
| 0 | 현재 작업 커밋 (미커밋 소스 전체) | — |
| 1 | **데이터 시딩** (§6) | 외부(faucet·체인). 실패를 먼저 발견한다 |
| 2 | 순수 모듈 + 단위 테스트 (§3) | 없음. 1단계 대기 중 병행 |
| 3 | 토큰 재정의 — 타이포·셸 (§1.1–1.2) | 없음 |
| 4 | `DecisionCard` + 아바타 + 조건 문장 (§2) | 2, 3 |
| 5 | 단일 컬럼 레이아웃 + 필터 칩 (§5) | 4 |
| 6 | REASON 원문 렌더 + **E2E S7** (§3.1–3.2) | 1, 4 |
| 7 | 스레드 섹션 + **E2E S6** (§3.4) | 1, 4 |
| 8 | E2E 보강 S1·S2·S3 (§8.4) | 1, 4 — `data-attester`·`data-block-number`가 4단계 산출 |
| 9 | **장식 레이어** — 괘선·브래킷·텍스처·번호·스크롤 애니메이션 | 5 — 카드 번호와 스크롤 등장이 레이아웃에 얹힌다 |

6·7·8·9는 서로 의존하지 않으므로 각각 독립적으로 중단할 수 있다.
S6은 7단계에, S7은 6단계에 딸린다 — 한 단계에 묶으면 중단 가능성이 사라진다.

### 9.1 최소 배포 단위에 대한 정직한 진술

0~5단계는 **기술적으로** 배포 가능하다. 그러나 1단계(시딩)가 실패하면
발행자는 여전히 한 명, 전건 검증됨, 임계값 전부 1원이다 —
§원인 2에서 스스로 진단한 문제가 그대로 남는다.
즉 **0~5단계는 시딩이 성공했을 때만 제품으로서 완결된다.**
2~5단계가 시딩 없이 "완성"된다는 말은 코드 기준이지 제품 기준이 아니다.

### 9.2 소요 추정

코덱스 리뷰 2회차 판정: 1~9단계 전체는 1인 + AI 에이전트로 29시간에 **신뢰할 수 없다.**
0~5단계는 faucet·트랜잭션이 즉시 성공할 경우 20~29시간에 들어갈 수 있다.

이 스펙은 그래서 자르는 대신 **순서로 대응한다.** 9단계(장식)와 6·7단계가
잘려도 앞이 무너지지 않도록 의존 방향을 한쪽으로만 두었다.
시간이 남으면 끝까지 가고, 모자라면 뒤에서부터 버린다.
