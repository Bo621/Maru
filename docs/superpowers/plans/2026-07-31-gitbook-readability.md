> 대상: `https://vestat.gitbook.io/maru/` · 저장소 `gitbook/` 21개 문서 1,303줄
> 목적: **이 문서만 읽는 심사자**가 막히지 않게 한다.

| 문제 | 근거 |
|---|---|
| 용어를 정의 없이 쓴다 | 도장 15회 · 활성 정산 17회 · 커밋 23회 · EAS 21회 · 스냅샷 22회 · 리졸버 11회 — **첫 등장 시 설명 없음** |

## 개선 A — 용어를 처음 쓸 때 풀어 쓴다

새 문서를 만들지 말고 **첫 등장 자리에서 한 번 설명**한다. 각주보다 본문 괄호가 낫다 —
GitBook 각주는 클릭해야 보인다.

| 용어 | 처음 쓰는 곳 | 넣을 설명 |
|---|---|---|
| 결정(decision) | `intro/what.md` | 「결과를 알기 전에 조건과 관측 구간을 못 박아 온체인에 올린 판단 한 건」 |
| 관측 구간 | `intro/what.md` | 「맞았는지 따질 때 쓸 시각 범위. 시작·끝이 분 단위로 고정된다」 |
| 커밋 | `intro/what.md` | 「원문 대신 해시만 먼저 올려 두는 것. 나중에 원문을 공개하면 누구나 대조할 수 있다」 |
| 도장 | `intro/what.md` | 「GIWA 의 지갑 인증(Verified Address). 그 지갑이 사람 확인을 거쳤다는 표시」 |

| EAS | `intro/deployed.md` | 「이더리움 어테스테이션 서비스. 서명된 기록을 온체인에 남기는 표준 규격」 |
| 리졸버 | `intro/deployed.md` | 「기록이 올라올 때 규칙을 검사하는 컨트랙트」 |

둔다. SUMMARY 맨 끝에 「부록 · 용어」로 등재.

## 개선 B — 그림 셋을 mermaid 로 넣는다

GitBook 은 ```mermaid 를 그대로 렌더한다. **세 곳만** 넣는다. 많이 넣으면 산만하다.

### B1. 판단 한 건의 일생 — `intro/what.md`

```
발행(조건·구간 고정) → 관측 구간 경과 → 정산 등록 → 검증
```
각 단계에서 **무엇이 바뀔 수 없게 되는지**를 함께 표시한다. 이게 제품의 전부다.

### B2. 화면 이동 — `design/screens.md`

지금 ASCII 도식으로 있는 것을 mermaid 로 바꾼다. 피드 → 프로필 → 결정 상세 → 검증.
`#/write` 는 지갑 필요 표시를 붙여 갈래로 그린다.

### B3. 판정이 나오는 경로 — `design/snapshot.md`

스냅샷 우선 → 없으면 실시간 조회 → 실패하면 판정 없음. 분기 그림이 필요한 유일한 곳이다.

**ASCII 도식 나머지 11곳은 그대로 둔다.** 표 형태로 정렬된 것들은 코드블록이 오히려 맞다.

## 개선 C — 문투 다듬기

### 고칠 패턴

> **실측으로 바로잡음.** 처음엔 「…하는 일과 하지 않는 일」 소제목이 반복된다고
> 적었는데 세어 보니 **1곳뿐**이었다. 실제로 티가 나는 건 아래 둘이다.

| 지금 | 실측 | 바꿀 방향 |
|---|---|---|
| 줄표(—) 남용 | **141회** / 1,303줄 | 한 문단에 최대 1회. 나머지는 문장을 나누거나 쉼표로 |
| 「…않는다」 부정형 나열 | **49회** | 하는 것을 먼저 쓰고 한계를 뒤에. 연속 3개 이상은 반드시 푼다 |
| 「…하는 일과 하지 않는 일」 | 1곳 | 내용에 맞는 제목으로 |

줄표가 가장 많은 문서: `design/screens.md`(13) · `protocol/no-contracts.md`(11) ·
`limits/not-done.md`(10).

### 대상 문서 — 심사자가 먼저 볼 순서

1. `README.md` (첫 화면)
2. `intro/what.md`
3. `intro/verify-in-5-min.md`
4. `problem/what-is-proven.md`
5. `limits/not-done.md`

**나머지는 손대지 않는다.** 시간이 한정돼 있고, 위 다섯이 읽힘의 8할이다.

### 지킬 것

- 사실을 바꾸지 않는다. 수치는 `docs/submission/FACTS.md` 에서만.
- 한계를 약화하지 않는다. 「실사용자 없음」·「데모 페르소나」·「로컬 팔로우」는 그대로 남긴다.
- 과장 형용사를 새로 넣지 않는다.

## 순서

```
1. glossary 신설 + SUMMARY 등재
2. 용어 첫 등장 설명 (개선 A)
3. mermaid 셋 (개선 B)
4. 표 셋 (개선 D)
5. 문투 다듬기 다섯 문서 (개선 C)
6. 링크 무결성·FACTS 대조 재검사
7. 커밋 → 푸시 → GitBook 자동 동기화 확인
```

## 검증

- `gitbook/` 내부 링크 전량 재검사
- 모든 수치를 `docs/submission/FACTS.md` 와 대조
- 라이브 사이트에서 mermaid 3개가 실제로 그려지는지 확인
- 한계 문서에서 빠진 항목이 없는지 대조 (실사용자·팔로우·코멘트·순위·MATCH 필터)

## 하지 않을 것

| | 이유 |
|---|---|
| 문서 새로 쓰기 | 재료는 충분하다. 진입점과 설명이 없었을 뿐 |
| POI 내용 복사 | 링크로 잇는다. 두 곳에 두면 반드시 어긋난다 |
| mermaid 남발 | 셋이면 된다. 그림이 많으면 아무것도 안 보인다 |
| 한계 축소 | 이 제품이 심사에서 먹히는 이유가 그건데 지우면 안 된다 |
