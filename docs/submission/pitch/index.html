// 01 한 장으로

결과를 알기 전에 고정한 판단이, 맞았는지까지 보인다

여러 지갑의 판단이 시간 역순으로 흐른다. 관측 구간이 끝나면 업비트 1분봉 재계산으로 맞음·틀림이 함께 뜬다. 틀린 판단도 지워지지 않는다.

고정한다

기존 POI 스키마에 지갑으로 직접 attest한다. 관측 구간은 결정 시점에 미리 선언된다.

“비트코인 원화 종가가
91,727,000원을 넘는다”

흐른다

피드는 여러 지갑의 판단을 시간 역순으로 나열한다. 순위나 추천 알고리즘이 아니다.

전체 · 팔로우 · 곧 결과 나옴
세 개의 탭

대조한다

구간이 끝나면 화면이 업비트 1분봉으로 재계산해 맞음·틀림을 표시한다. 발행자가 정할 수 없다.

// 02 문제

스크린샷은 증명이 아니다

트레이더 커뮤니티에서 수익률은 스크린샷과 평판으로 오간다. 포토샵도 되고, 맞은 것만 골라 올리는 것도 된다.

수익률 캡처사후 편집·합성 가능
SNS 예측 게시글지우면 그만, 맞은 것만 남길 수 있다
평판·팔로워 수과거 발언 전체를 대조할 방법이 없다
// 03 기존 방식이 막지 못하는 것

남는 건 사후 서사다

결과를 본 뒤에는 누구나 이렇게 말할 수 있다 — “나는 그럴 줄 알았다.” 캡처·게시글·평판 중 어느 것도 이 말이 결과 전에 있었는지를 증명하지 않는다.

지금

맞힌 판단은 캡처로 남기고, 틀린 판단은 지운다. 지운 사람과 안 지운 사람이 화면에서 구별되지 않는다.

새 구독자는 결국 “요즘 잘 맞힌다더라”는 평판으로 고른다.

마루 이후

판단은 결과를 알기 전에 온체인에 고정된다. 발행자가 나중에 지우거나 고칠 수 없다.

관측 구간이 끝나면 맞음·틀림이 화면 재계산으로 붙는다. 틀린 것도 피드에 그대로 남는다.

// 04 해법

결과 전에 조건과 관측 구간을 고정한다

// 05 SNS 의 최소 조건과 우리의 답

로그인 · 작성 · 팔로우 · 추천 피드 — 각각 무엇으로 답했나

최소 조건무엇으로 답했나
로그인지갑 연결(EIP-1193) — 별도 계정·비밀번호 없음
작성기존 decision 스키마에 attest — 새 컨트랙트 불필요
팔로우브라우저 로컬 저장 — 온체인이 아니다. 화면에 그렇게 밝힌다
추천 피드만들지 않았다. 시간 역순 나열 + 조건부 필터(도장 검증·정산 건수)로 대신한다

추천 알고리즘 대신 필터를 둔다. 필터는 URL 쿼리에 남아 링크로 공유된다 — 「이 조건으로 거른 피드」를 남에게 보낼 수 있다.

// 06 실제 화면 ① 피드

맞음과 틀림이 함께 뜬다

관측 구간이 끝난 결정에는 업비트 1분봉 재계산 결과가 붙는다. 틀린 판단도 숨기지 않는다.

인장이 상태를 말한다

등록완료·지연등록이 각 결정 왼쪽에 붙는다. 둘 다 「화면 재계산 맞음」이 함께 표시된다.

도장 검증과 팔로잉이 나란히

발행자 주소 옆에 도장 검증 — TESTNET FAUCET 라벨과 팔로잉 상태가 함께 보인다.

UID로 열어 대조한다

각 줄 우측의 결정 열기가 상세 화면으로 이어진다. 관측 구간과 UID가 함께 남는다.

지금 열립니다 — maru-web-production-0407.up.railway.app · 결정 0x5941a398…443888

// 07 실제 화면 ② 이유 원문

해시가 맞을 때만 인용된다

발행자가 남긴 이유 원문은 인용 블록으로 보인다. 이 문장의 해시가 결정에 기록된 커밋과 일치할 때만 인용으로 뜬다 — 파일을 고치면 표시가 사라진다.

원문은 커밋의 증거지, 커밋이 원문을 만들지 않는다

결정 커밋 시점에는 해시만 온체인에 남는다. 원문 공개 후에야 대조가 가능해진다.

필터의 한계를 필터 바로 아래 적는다

「정산이 등록됐다는 뜻이지, 관측값이 맞다는 뜻이 아닙니다」 — 걸러 준다고 보증하지 않는다.

이 피드의 기록은 데모 페르소나다

필터 위에 「이 피드의 기록은 시연을 위해 발행한 데모 페르소나의 판단입니다」가 먼저 뜬다.

지금 열립니다 — maru-web-production-0407.up.railway.app

// 08 실제 화면 ③ 곧 결과 나옴

기다리는 상태가 그대로 보인다

아직 관측 구간이 끝나지 않은 판단은 대기 인장으로 남는다. 결과를 앞당겨 보여주지 않는다.

대기는 맞음도 틀림도 아니다

구간이 열려 있는 동안은 대기로만 표시한다. 조기 판정을 만들지 않는다.

이 목록도 순위가 아니다

「이 목록은 조회된 기록의 나열입니다」와 「조회된 것이 전부라는 보장은 없습니다」가 같은 자리에 반복된다.

구간이 닫히면 같은 UID가 재계산된다

결정 열기로 들어가면 관측 구간 종료 시점의 재계산 규칙이 그대로 적힌다 — 화면이 만들어내지 않는다.

// 09 신뢰 경계

무엇이 증명되고 무엇이 안 되나

컨트랙트가 강제 — POI 불변식

관측 구간이 커밋 이후여야 한다 · 정산 산술이 관측값과 일치해야 한다 · 입장 변경(parents)의 선후 관계가 지켜져야 한다.

화면이 재계산해 표시

맞음·틀림 — 업비트 1분봉으로 재계산한다 · 이유 원문 — 해시가 결정의 커밋과 일치할 때만 인용으로 보인다.

보장하지 않음

실사용자·활성도(피드 기록은 데모 페르소나다) · 온체인 팔로우(브라우저 로컬 저장) · 관측값 자체의 진실성 · 조회된 기록의 완전성.

검증기 MATCH는 「예측이 맞았다」가 아니라 「등록된 관측값이 재계산과 같다」다. 화면이 「틀림」으로 표시한 결정도 검증기에서는 MATCH다.

// 10 새 컨트랙트 0개

같은 프로토콜, 다른 제품 표면

마루는 POI 프로토콜(Track 03 지원) 위에 있다. 새 컨트랙트를 배포하지 않고, 이미 배포된 스키마로만 읽고 쓴다. 같은 심사팀이 두 지원서를 본다 — 먼저 밝힌다.

소셜 기능무엇으로 되나새 컨트랙트

새 컨트랙트가 필요한 칸은 두 개뿐이고, 둘 다 이번 범위 밖이다. 소셜 표면은 이미 배포된 POI 컨트랙트 4종을 읽고 쓰는 것만으로 선다.

// 11 왜 GIWA 인가

판단 하나를 원 단위 비용으로 고정한다

GIWA Sepolia(chainId 91342)의 낮은 L2 비용이 결정 하나마다 온체인에 커밋하는 것을 실용적으로 만든다. 판단을 올리는 비용이 원 단위인 체인에서만 「사람들이 실제로 이걸 쓰는가」를 물을 수 있다.

EAS 프리디플로이Ethereum Attestation Service — 증명 기록 표준. GIWA 기본 탑재
스키마·발급·철회를 재구현하지 않는다. 새 신뢰 축을 세우지 않는다
도장 Verified Address도장 = GIWA 의 온체인 신원 인증
발행자 주소 옆 「도장 검증 — TESTNET FAUCET」 라벨로 이미 연동돼 화면에 뜬다
저비용 L2결정 단위 커밋과 소셜 피드 열람의 경제성

POI가 이미 이 체인 위에서 증명 레이어를 돌린다. 마루는 그 위에 사람이 보는 표면만 올린다 — 새 신뢰 가정을 추가하지 않는다.

// 13 심사자가 5분에 확인하는 법

S1~S10 — 지갑 없이

S5발행자 → Passport → 결정 상세 → 「검증하기」 → 오프체인 재현까지 이어진다
S6스레드 배지가 붙은 결정을 누른다 → parents DAG(입장 변경 이력)로 이어진다
S7이유 원문이 인용 블록으로 보이고, 해시가 맞는 것에만 일치 표시가 붙는다

S9팔로우를 누르고 팔로우 탭으로 간다 → 「이 브라우저에만 저장됩니다」 고지가 보인다
S10「곧 결과 나옴」 탭 → 아직 창이 안 닫힌 판단이 마감 임박 순으로 뜬다

작성(S11~S12)만 GIWA Sepolia 지갑이 필요하다. S12가 핵심이다 — 결과를 알기 전에 고정하는 것 말고는 판단을 올릴 방법이 없다.
