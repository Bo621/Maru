# 월렛 탑재 가능성

> **탑재는 아직 검증되지 않았다.** 실제 GIWA 월렛 안에서 마루가 동작하는지
> 확인한 적이 없다. 아래는 「담길 수 있다」가 아니라 **「왜 여기에 있어야
> 하는가」**를 적은 것이다. POI의 [같은 제목 문서](https://vestat.gitbook.io/poi/giwa/wallet)도
> 같은 태도로 「후보 구조로 서술」한다. 마루는 소비자 표면 쪽에서 같은
> 질문에 답한다.

## 왜 지갑인가: 소셜 피드의 자연스러운 자리

마루가 보여주는 것은 「내가 팔로우한 사람의 판단」이다. 지갑은 이미
사용자가 누구인지, 그리고(도장을 통해) 어떤 자격을 증명했는지 알고 있다.
지갑 밖 서비스는 이걸 사용자에게 다시 물어봐야 하고, 묻는 순간
「본인이 원할 때만, 유리한 것만」 보여주는 선택적 경험이 된다. 지갑 안에서는
그럴 필요가 없다.

```
지갑 밖 (지금)                    지갑 안 (후보)
─────────────                    ─────────────
팔로우한 사람 찾기 → 마루 열기      팔로우 목록이 이미 지갑에 있다
지갑 연결 → 서명                  이미 연결된 지갑으로 그 자리에서 서명
결과 보러 다시 마루 방문           알림으로 결과를 받는다
```

## 지갑 안에서 성립하는 흐름

1. **팔로우한 사람의 판단을 본다.** 피드의 팔로우 탭과 같은 데이터, 다른
   진입점이다.
2. **그 자리에서 발행한다.** 결과를 알기 전에 조건과 관측 구간을 고정하는
   행위 자체가 지갑 서명 하나로 끝난다. 마루가 하는 일은 화면을 그리는 것
   뿐이다.
3. **결과를 확인한다.** 관측 구간이 닫히면 맞음·틀림이 붙는다. 지갑 안에서
   이 알림을 받을 수 있다면, 지금처럼 사용자가 직접 다시 방문해 확인할
   필요가 없어진다.

## 임베드 조건: 확인된 사실

| | |
|---|---|
| 백엔드 | **없음.** 정적 파일 + RPC 직접 호출 |
| 라우팅 | 해시 라우팅 `#/feed`, `#/d/<uid>` — 라우터 라이브러리 없음 |
| 지갑 인터페이스 | EIP-1193만 요구 |
| 지갑 없이 | 조회·필터·검증 전부 동작(발행만 지갑 필요) |
| 배포 | Railway 정적 호스팅, POI와 별도 서비스 |

이 조건들은 POI 화면과 같다. 같은 팀이 같은 방식으로 만들었기 때문이다.
GIWA 월렛이 POI 임베드를 검증하면 마루도 같은 경로를 탈 가능성이 높다.

## 아직 확인하지 못한 것

- 월렛은 웹 콘텐츠를 어떤 방식으로 임베드하는가? (iframe / WebView / 별도 탭)
- 해시 라우팅·새로고침에 제약이 있는가? 팔로우 탭(`#/feed?tab=follow`)처럼
  쿼리가 붙은 딥링크가 그대로 열리는가?
- EIP-1193 서명 UX는 외부 브라우저와 어떻게 다른가? 발행(`#/write`)이 한
  번의 서명으로 끝나는 흐름을 유지할 수 있는가?
- 결정 상세(`#/d/<uid>`)나 팔로우 필터가 걸린 상태로 딥링크하는 규격은
  무엇인가?

**규격을 모르는 채 만들면 추측이 코드가 된다.** 그래서 월렛용 manifest나
SDK adapter는 이 질문들의 답이 나온 다음 범위다. 그 답을 GIWA 팀에게 듣는
것이 다음 단계에서 가장 필요한 지원이다.
