# 판정 관측값 스냅샷

`public/verdicts.json`에 관측이 끝난 구간의 봉을 담아 둔다. 갱신은
`node scripts/build_verdict_snapshot.mjs`다.

## 왜 필요한가

배포 출처(Railway)에서는 업비트 API 요청이 대부분 막힌다
(`TypeError: Failed to fetch`). 닫힌 관측 구간의 값은 결과가 이미 확정된
과거 데이터라 불변이므로, 빌드 시점에 미리 계산해 담아 두면 배포 환경에서
업비트를 못 불러도 심사자가 보는 화면에서 판정이 뜬다.

## 담는 것: 판정이 아니라 관측에 쓴 봉 하나

```json
{
  "version": "maru.verdict-snapshot.v1",
  "generatedAt": "2026-07-30T14:33:04.689Z",
  "observed": {
    "0x3f592f21a7e5a733d3dd90caeb2f9ec35bffa335b69da7310749694283e16938": {
      "startedAt": "1785343260",
      "close": "91727000"
    }
  }
}
```

**술어 계산(맞음/틀림 판정)은 `src/verdict.ts`의 `decideVerdict` 한 곳에만
남는다.** 스냅샷이 판정 자체("match"/"mismatch")를 담으면, 화면이 관측 규칙을
바꿔도 스냅샷의 낡은 판정이 계속 표시돼 화면과 검증기가 갈라질 수 있다.
그래서 스냅샷은 원재료(봉 하나)만 담고, 판정은 매번 그 봉으로 다시 계산한다.

## 조회 우선순위

`useVerdicts.ts`는 각 결정에 대해 스냅샷을 먼저 찾는다. 있으면 네트워크를
타지 않고 즉시 판정한다. 없는 결정만 업비트를 실시간으로 조회한다. 관측이
막 끝난, 아직 스냅샷에 없는 결정이다.

재시도 스케줄은 실시간 조회로 떨어진 것만 대상이다. 스냅샷으로 즉시
해결된 행은 타이머 없이 그대로 끝난다.

## 배포 환경에서 실시간 조회는 안정적으로 성립하지 않는다

업비트는 브라우저 Origin 요청을 10초당 1회로 제한한다(공식 정책). 관측이
끝난 구간은 배포 시점에 계산해 담아 둔 스냅샷 값이고, 그 뒤에 새로 끝난
구간은 화면이 직접 조회하는데, 이 제한 때문에 바로 뜨지 않을 수 있다.
실측(스냅샷을 강제로 끊은 상태): 9건 요청 중 1건만 200, 8건이 429였고,
15초 뒤에도 16행 중 2행만 판정이 떴다. 스냅샷을 다시 만들면(빌드 시점
재계산) 그 구간도 채워진다.

## 파싱 실패의 처리는 실패 범위에 따라 다르다

`parseVerdictSnapshot`은 JSON 파싱 실패·버전 불일치·최상위 구조 오류(`observed`가
객체가 아닌 경우)에서 **빈 Map을 돌려준다.** 반면 `observed` 안의 개별 항목
하나가 형식에 안 맞으면(정수 문자열이 아닌 `startedAt` 등) 그 항목만 건너뛰고
나머지는 그대로 담는다. 스냅샷 파일 전체가 깨졌을 때만 화면 전체가 실시간
조회 경로로 떨어지고, 항목 하나가 깨졌을 때는 그 결정만 실시간 조회로
떨어진다.

## 생성 스크립트가 재구현하지 않는 것

`scripts/build_verdict_snapshot.mjs`는 관측값을 고르는 로직(`pickObservedClose`)과
업비트 조회(`fetchWindowCandles`)를 `src/` 그대로 import해서 쓴다. 스크립트
안에서 같은 로직을 또 구현하는 대신 import 하나로 유지한다. 두 벌이 되면 언젠가 갈라진다.
