# 화면 구조와 라우팅

## 라우팅

해시 라우팅이다. 라우터 라이브러리 없이 `window.location.hash`를
`useSyncExternalStore`로 구독한다(`src/router.ts`). 백엔드가 없으므로 서버
사이드 라우팅이 성립하지 않는다 — 정적 파일 하나가 모든 경로를 받는다.

| 경로 | 화면 | 지갑 필요 |
|---|---|---|
| `#/feed` (또는 빈 해시) | 공개 피드 | 아니오 |
| `#/p/<address>` (`#/passport/<address>`도 호환) | 발행자별 기록 | 아니오 |
| `#/d/<uid>` | 결정 상세 | 아니오 |
| `#/verify/<uid>` | 검증 안내 | 아니오 |
| `#/write` | 판단 발행 | **예** |
| 그 외 | 없는 화면 | — |

주소·UID는 파싱 시점에 소문자로 정규화한다(`ADDRESS_PATTERN`/`UID_PATTERN`).
대소문자 비교가 세 번 문제였던 POI의 경험을 반복하지 않기 위해서다.

## 피드 필터 — 순수 함수로 뺀 이유

`src/filter.ts`의 `filterFeedItems`는 부수효과가 없는 순수 함수다.

```ts
export interface FeedFilter {
    verifiedOnly: boolean;
    settledOnly: boolean;
    minimumSettled: number;
}
```

`verifiedOnly`는 `verifiedAddressUID`가 32바이트 0이 아닌지만 본다.
`minimumSettled`는 `settledOnly`가 켜지면 최소 1로 강제된다 — 체크박스 하나와
숫자 입력 하나가 사실은 같은 축의 필터라는 뜻이다.

순수 함수로 뺀 이유는 **뮤테이션 테스트**다. 조건 하나를 지우고 `pnpm test`를
돌렸을 때 여전히 통과하면 그 테스트는 무의미하다 — PLAN.md가 직접 쓴 원칙이고,
`TESTPLAN.md` 4번 항목이 배포 게이트에 넣었다.

## 탭 — 성과 순위를 만들지 않는 세 가지 정렬

`src/feedTab.ts`가 URL의 `tab` 파라미터로 세 가지 행 선택을 한다.

| 탭 | 무엇으로 고르나 |
|---|---|
| 전체 | 입력 순서 그대로 — 체인에서 읽은 시간 역순 |
| 팔로우 | 로컬 팔로우 목록에 있는 발행자만 |
| 곧 결과 나옴 | `windowEnd > now`인 결정만, 마감 임박 순(오름차순) |

**셋 다 시간이나 사용자 선택이지 성과 지표가 아니다.** 정렬 선택지를 따로
주지 않는 것도 같은 이유다 — 순위를 만들지 않기 위해서다.

## 상태 넷 — 전부 만든다

| 상태 | 화면 |
|---|---|
| 불러오는 중 | 로딩 스탬프 + 안내 문구. 빈 화면을 보여주지 않는다 |
| 하나도 없음 | 「이 조건에 맞는 판단이 없습니다」 + 조건 지우기 링크 |
| 오류 | 「불러오지 못했습니다」 + 원인 메시지 + 다시 읽기 버튼 |
| 일부 실패 | 읽은 것은 보여주고, 실패한 UID는 회색 오류 행으로 남긴다 |

마지막 행이 중요하다. 조용히 빼면 「조회된 것이 전부가 아니다」라는 화면의
문구와 어긋난다. `readDecision`은 스키마를 검사하고(`assertSchema`), 다른
스키마 UID가 섞이면 던진다 — `Promise.allSettled`로 감싸 실패한 건을
행에서 빼지 않고 오류로 표시한다.

## 90,000블록 청크와 마지막 `latest`

공개 RPC가 `eth_getLogs`를 90,000블록 단위로 제한한다. `DEPLOY_BLOCK`부터
청크로 나눠 읽고, 마지막 청크는 `toBlock: "latest"`를 써야 한다. 캐시된
`getBlockNumber`를 `toBlock`으로 쓰면 방금 채굴된 블록을 놓친다 — 실제로
겪었고 단위 테스트가 이 회귀를 고정해 둔다(`test/read.test.ts`).

## 카드 하나 — 피드와 프로필이 공유

`DecisionCard`(`src/card.tsx`)를 피드와 프로필 화면이 함께 쓴다. 같은 결정을
두 화면이 다른 마크업으로 그리면 언젠가 갈라진다.

## 판단 상세는 만들지 않는다

결정 상세(`#/d/<uid>`)는 조건식·정산 상태·스레드까지 보여주지만, 판단 자체를
「깊게 파는」 화면은 POI가 이미 가지고 있다. 같은 화면을 두 번 만들면 두
제품이 같아 보인다 — 결정 카드의 「열기」는 마루 안의 상세로, 「검증하기」는
POI verifier 안내로 이어진다.
